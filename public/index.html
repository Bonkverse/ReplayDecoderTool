How replays work


      
What is a replay?

      
A bonk.io replay is not a video. It's a recipe for re-running one round: the map and starting positions, who was playing, the room settings, and a list of every key each player pressed and when. bonk.io's physics is deterministic, so if you start from the same state and feed in the same keys at the same steps, you get the exact same game every time.

      
The physics runs at 30 steps per second. "Step" (or "frame") just means one tick of that clock.


      
What's inside one

      
    
        
  • playerArray — one entry per player slot: userName, level, team, guest, and their skin (avatar).
    • 
        
  • startingState — the world at step 0: the map (mm for its info, plus its physics), every player's position and speed, scores, the random seed, and the round count.
    • 
        
  • inputs — the gameplay. A packed list of "player X changed their keys to Y at step Z". Only changes are saved: a key stays held until the next change.
    • 
        
  • adminInputs — rare host actions during the round.
    • 
        
  • gameSettings — mode (mo: b classic, ar arrows, ard death arrows, sp grapple, v VTOL, f football), teams on/off (tea), win limit (wl).
    • 
        
  • es — the end step, so es ÷ 30 is the length in seconds.
    • 
        
  • mn, ma, mid — map name, author, and id, repeated at the top for convenience.
    • 
      


      
How bonk.io packs it into a string

      
To send a replay over the web, bonk.io squeezes that object into one long piece of text. It does four things in a row:

      
replay object
   │ 1. PSON          compact binary JSON (common words become 1-byte codes)
   ▼
bytes
   │ 2. base64        bytes → plain text (A–Z a–z 0–9 + /)
   ▼
base64 text
   │ 3. LZString      compress, using only URL-safe characters
   ▼
compressed text
   │ 4. case flip     swap upper/lower case on the first 101 characters
   ▼
replaydata  ← what the bonk.io API hands out


      
Decoding = the same steps backwards

      
Every step can be undone exactly, so decoding is just steps 4 → 1 in reverse: flip the case back, LZString-decompress, base64-decode, then PSON-decode. That's what the Decode tab does.


      
Encoding = the steps forwards

      
The Encode tab runs steps 1 → 4. Because nothing is lost along the way, encoding a replay you just decoded gives back the exact same string, character for character. The tool checks this for you after every encode.


      
Each step, in plain words

      
    
        
  1. PSON is like JSON but stored as bytes instead of text, which makes it smaller. It also has a shared word list (the "dictionary"): words like physics or shapes get written as a tiny number. Both sides need the same list in the same order, or the words come out wrong.
    2. 
        
  2. base64 turns raw bytes into safe text characters so they can travel inside a web request. It makes data about a third bigger.
    3. 
        
  3. LZString is a compressor (it finds repeated bits and replaces them with short references), then writes the result with URL-safe characters.
    4. 
        
  4. Case flip is a small bonk.io quirk. It isn't encryption. It just means a string won't decompress unless you flip it back first.
    5. 
      


      
The inputs inside the inputs

      
After decoding, inputs is still a base64 string. Unpacked, it's a list of 7-byte records: player slot (2 bytes), step (4 bytes), and the keys (1 byte). The keys byte uses one bit per key: left = 1, right = 2, up = 4, down = 8, heavy = 16, special = 32. So 5 means left + up held. The Decode tab shows the first few of these in the Inputs table.


      
How Bonkverse stores replays

      
The scraper decodes each replay down to the PSON bytes, gzips them, and stores those in Postgres. That's 40–60% smaller than the original string, and since every step is reversible, the original string can be rebuilt any time with the encoder.
